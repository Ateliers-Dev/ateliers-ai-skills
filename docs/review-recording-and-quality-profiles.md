# レビュー記録と品質プロファイルの運用判断

> 作成日: 2026-11-23
> 対象: ateliers-pr-review と、それを呼び出す人・AI・Orchestrator
> 状態: 共通の運用判断。プロジェクト固有の手順・権限は各リポジトリの規則に従う。

この文書は、レビュー結果をどこへ記録するかと、レビュー前に品質条件をどう決めて渡すかを説明します。ateliers-pr-review Skill の独立性を保つため、特定の Orchestrator、契約スキーマ、GitHub 接続、投稿権限を必須にしません。小規模な作業では、以下の判断を短い Review Plan と記録で満たせます。例は判断の仕方を示し、全ての成果物へ一律に追加する要件ではありません。

## 1. 役割と記録先

| 役割 | 責務 | 権限境界 |
| --- | --- | --- |
| Reviewer | 対象 SHA・計画・範囲を確認し、指摘、根拠、技術的 Severity、指摘単位の Gate 影響、未確認事項を含むレビュー結果を作る | 既定で読み取り専用。結果作成だけで投稿・修正・Gate 通過・マージ承認を行わない |
| Implementer | 変更を実装し、指摘への応答、修正 SHA、検証方法・結果・証跡を提示する | 自身の変更を独立レビュー済みとは扱わない。未解決指摘の扱いを単独で承認しない |
| 記録担当 | 受け取った結果の対象リポジトリ・PR・head SHA・投稿先を照合し、権限と明示依頼の範囲で外部記録する。投稿の成否と参照先を確認する | 結果の技術的内容や Severity を書き換えず、承認・マージ・リリース判断を代行しない |
| 計画・Gate 判断者 | レビュー前に目的・段階・完了条件・安全下限・検証証跡と、必要な承認者を定める。結果を条件と照合し、条件変更・残余リスク・進行を判断する | 権限はプロジェクト規則に従う。マージ・提供判断は個別の人間の権限に残す |

役割は機能であり、運用に応じて同じ人や AI が複数を担えます。ただし、独立レビューが必要な場合は、Implementer と Reviewer を分けます。Reviewer が読み取り専用で結果を返す運用では、記録担当が結果を受領して投稿します。

### PR と Issue の使い分け

- **Pull Request** は、特定の変更と head SHA に関するレビュー所見、行位置と根拠、修正への応答、対象 SHA の検証結果を記録する一次記録です。レビューを更新する場合は、前の結果を消さず、どの SHA に対する追記・再評価かを示します。
- **Issue** は、作業の進捗、完了報告、範囲を越えて後続対応する指摘、技術的負債の状態を追跡する場所です。完了報告では成果・証跡・未解決事項・残リスクを要約し、詳細なレビューがある PR を参照します。
- PR に既に残るレビュー全文を Issue に複写しません。Issue から PR を参照し、PR から後続 Issue を参照します。Issue が存在しない、または作成が許可されていない場合は、報告案を呼び出し元へ返して扱いを決めてもらいます。
- P1/P2/P3 の Severity は対象プロジェクトの定義を使用します。各指摘には、確認できる根拠（ファイルと該当版の行、または文書の見出し）、発生条件・影響、修正または次の対応を添えます。正確な位置が分からない場合は作らず、その旨を示します。Severity と Gate 影響の定義・分離は [Reviewer Skill の説明](pr-review.md)を参照してください。

## 2. 投稿方式の比較と採用

| 方式 | 良い点 | 注意点 |
| --- | --- | --- |
| Reviewer が直接投稿 | 手渡しが少なく、評価と記録が近い | 読み取り専用の独立 Reviewer と投稿権限が結合し、再試行・重複・投稿後確認まで Reviewer が抱える。単独利用や GitHub 未接続では使えない |
| Orchestrator が集約・投稿 | 複数工程の結果と対象 SHA を一か所で照合し、形式を揃えやすい | Orchestrator がない利用を排除しないよう、共通 Skill の必須依存にできない。実装固有の状態・権限管理が必要 |
| 独立した記録担当（人または AI）が投稿 | 読み取り専用の Reviewer と外部操作を分離し、Orchestrator の有無に左右されにくい | 結果、対象 SHA、投稿状態を確実に引き渡す契約と確認が必要 |

**採用するのは、機能としての「記録担当が投稿する」方式です。** Orchestrator を使う運用では Orchestrator が記録担当を担ってもよく、使わない運用では権限を持つ人または別の担当 AI が担えます。Reviewer 直接投稿は、依頼で投稿が明示され、その Reviewer に必要な権限が与えられ、独立性を損なわない運用に限る例外です。この選択は、#22 で挙げられた読み取り専用 Reviewer と担当分離を尊重しながら、複数の呼び出し形態を残します。

### 重複・失敗・権限不足・結果不明

- 投稿前に同じ PR/Issue、対象 SHA、指摘 ID または完了報告を確認します。同じ記録が既にあれば再投稿せず、その記録を参照します。更新結果は新しい SHA と変更点を明記して追記します。
- 投稿の失敗が確認できたら、内容と投稿先を保持し、権限のある担当へ失敗と再開条件を返します。権限不足を回避するために権限を広げたり、別アカウントを探したりしません。
- 成功・失敗の応答がなく結果不明なら、再試行の前に投稿先を読み直して既存記録を確認します。見つかれば成功として参照し、なければ権限のある担当が再投稿を判断します。状態が確定するまで成功扱いしません。
- 二重通知を避け、Issue の進捗コメントには詳細 PR 記録へのリンクを置きます。投稿状態が不明のままならその状態も報告し、完了報告と誤認させません。
- 投稿・通知は人の承認やマージ判断の代わりではありません。外部への書き込みは、リポジトリの権限規則と当該作業で明示された依頼の範囲で行います。Skill の実行やレビュー依頼だけから書き込み許可を推定しません。

## 3. 品質条件を決めて渡す責務

品質条件を定めるのはレビュー前の計画・Quality Gate の機能です。計画担当は、分かる範囲で次を Review Plan に含め、Reviewer に渡します。小さなレビューでは PR 本文や依頼文の短い要約で構いません。

- 成果物の目的：Sample / Experiment / PoC / MVP / Product
- 提供段階：内部利用 / Closed Beta / Open Beta / 正式公開・継続運用など（成果物の目的とは別軸）
- 利用者・環境、実行リスク、納期等の制約
- 今回の範囲・対象外、成功条件・受け入れ条件
- 変更できない安全下限、必須のレビュー・検証と必要証跡
- 指摘の Gate 影響を判断する役割と、条件・残余リスクを承認できる人

Reviewer は与えられた条件に照らして各指摘を独立に評価し、技術的重大度（Severity）と指摘単位の Gate 影響（Block / Conditional / Advisory 相当）を分けて報告します。Severity は段階に合わせて下げません。各指摘の Gate 影響は、合意済みの完了条件・安全下限・根拠に結び付けます。レビュー結果は全体 Gate やマージ・リリースを決めません。Gate 担当者が全条件と証拠を照合し、必要な人間の承認を得ます。

### 未指定・矛盾・途中変更

- **品質プロファイルが未指定**：Reviewer は PoC/MVP/Product のラベルだけから合否条件を作りません。結果を左右する目的、受け入れ条件、安全下限が欠ける場合はその不足と影響を示し、必要に応じて確認します。独立して確認できる部分は続けます。安全条件や残余リスクを評価できない場合、Gate 判断者はその条件が確定するまで進行を判断できません。
- **条件が矛盾する**：計画担当へ矛盾と影響を返し、権限者の解決まで競合する条件について Gate を通過扱いにしません。Reviewer が都合のよい条件を選んだり、安全下限を緩和したりしません。
- **レビュー中に条件を変える**：レビュー担当は発見した事実を報告し、元の条件で評価を続けます。権限者が変更を決めた後、変更内容・理由・影響を Review Plan に記録し、影響を受ける指摘・検証を再評価します。AI 単独で品質を下げる変更は承認しません。

## 4. 共通の安全下限と段階別 Gate の例

PoC・MVP・Product や提供段階によってテスト量、運用準備、修正時期は変わります。次の安全下限はどの段階でも省略できません。

- 秘密情報を不必要に露出・記録・送信しない。検出した秘密を報告へ複製しない。
- 許可されていない破壊的操作や外部への副作用を行わない。対象・権限を明確にし、不可逆操作には合意された保護・確認を設ける。
- 実データの損失・破損を放置してよいことにしない。必要なアクセス制御・バックアップ・復旧条件は実行リスクと提供範囲に合わせて計画する。
- 権限境界やデータ保護が不明なとき、安全と推定して実行しない。既存の fail-closed 要件を維持し、重大な危険を隠したり Severity を下げたりしない。

以下は同じ技術的指摘が目的・環境で異なる Gate 影響を持ち得る例です。P2 は例示用の共通プロジェクト分類であり、実案件では対象リポジトリの Severity 規則に従います。

| 例（技術的 Severity は同じ P2） | PoC: 隔離された使い捨て合成データ環境 | MVP: 限定利用者・限定環境 | Product: 継続提供 |
| --- | --- | --- | --- |
| タイムアウト後、再試行待ちが無期限に続く | 主目的の実現可能性と安全下限に影響しないなら Advisory。検証時間・再実行条件を記録 | 主要価値を検証できない、または利用者を停止させるなら Conditional。時間上限・手動停止・対象制限を計画して人が受容するか判断 | SLA/完了条件や運用復旧に関わり、停止・資源枯渇を招くなら Block。制限付き再試行と監視・復旧証跡を確認 |
| 同じ処理が再実行され、作業が重複する | 合成データだけで影響を捨てられる場合は Advisory。限界を記録 | 評価結果を歪める、または限定環境内の状態を壊すなら Conditional。リセット可能性と条件を確認 | 実データ・外部副作用に二重適用し得る場合は Block。冪等性、重複防止、復旧方法を確認 |

これは段階ラベルによる自動判定表ではありません。同じ P2 でも、実際の影響、合意済み条件、安全下限、隔離・回復可能性を根拠に Gate 影響を決めます。実データ損失や許可のない破壊的操作など安全下限に触れる場合は PoC/MVP でも Block 相当として扱い、権限者が軽減策・範囲変更を決めるまで無条件に許容しません。Product でも、要求外で安全下限にも触れない改善提案を自動的に Block しません。

## 5. 未解決指摘と技術的負債

レビュー担当は所見と根拠を報告し、計画・Gate 判断者が今回修正するか後続へ送るかを決めます。範囲外の指摘を後続 Issue にするかどうかも、影響と追跡価値に基づき判断します。重大な安全下限違反や合意済み必須条件の未達を、Issue 化しただけで解決済みとはしません。

後続対応を Issue 等へ移す場合は、詳細な PR 所見を複写せず参照し、追跡に必要な情報を記録します。

- 元 PR・対象 SHA・指摘 ID・根拠へのリンク
- 対応しない／延期する理由、現在の影響と残余リスク
- 対応責任者または決定主体、対象段階・期限・見直し条件（決まっている場合）
- 対応状態と、再確認・再レビューが必要となる条件

期日を設定していない作業に架空の期限を付けず、責任者等が未定なら未定と記録します。完了時は Issue から修正 PR と検証証拠へリンクし、元の指摘を解消・軽減・受容のいずれとして扱ったか更新します。これにより技術的負債は将来の課題として可視化されますが、今回の Gate 結果やマージ判断は人の記録で別途残します。

## 6. 品質判断の構成案と採用理由

| 構成案 | 利点 | 留意点 |
| --- | --- | --- |
| 単一 Skill 内で条件整理とレビューを行う | 単独利用・他 AI から使いやすく、受け渡しが少ない | 計画条件の設定者と独立 Reviewer が同じ実行主体になる運用では、独立性・条件の固定が曖昧になり得る |
| Reviewer の前段に短い Planning 入力・手順を置く | 条件と承認境界をレビュー前に明示でき、Skill の呼び出し方式に依存しない | 計画責務の割当てと Review Plan の受け渡しは利用側が必要 |
| 独立 Quality Planner エージェントを置く | 複雑な複数工程で計画を集約できる | 常設の追加主体、権限・証跡・引継ぎ・障害点を増やし、小規模・単独利用には過剰 |

**採用するのは、レビュー前に Review Plan を用意する機能上の前処理です。** これは専用 Skill や新しいエージェントを必須にせず、呼び出し元の人、計画担当 AI、Orchestrator が実行できます。Skill 単独利用では、入力から目的・条件を短く整理し、判断を左右する不足だけ確認できます。明示条件や推定を区別して独立レビューに渡します。この構成は #23 のレビュー中の範囲固定を再実装せず、#24 が扱うレビュー前の条件決定と伝達を担います。Review Plan を渡せる特定契約形式は要求しません。
