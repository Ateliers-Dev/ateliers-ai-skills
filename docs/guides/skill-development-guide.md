# Skill 開発・運用の操作手順

作成日：2026-11-06 ／ 更新日：2026-11-06（日本標準時 JST (UTC+09:00)）

このガイドは、利用者が既存 Skill を使って作成・レビュー・改善・Issue 管理を進める操作例です。役割と判断の全体像は[開発ワークフロー](../skill-development-workflow.md)、Skill ごとの詳しい説明は[docs の入口](../README.md)を参照してください。各工程の結果を確認してから、利用者が次の作業を明示的に依頼します。Skill 同士が自動で連携するわけではありません。

## 1. 始める前の準備

1. 作業環境で必要な Skill が利用できる状態か確認します。ローカル Codex で全 Skill をユーザー領域へ配置する場合は、[Windows インストール手順](skill-installation.md)を参照します。他の環境の配置方法は[各 AI ツールでの使い方](../ai-tools.md)を確認してください。
2. GitHub 上の作業では、対象リポジトリとブランチを明示し、実際に使うアプリ・エージェントがリポジトリを読めるか確認します。接続や権限が確認できない場合は、ローカルファイルや差分を使える範囲で渡し、アクセスできたように扱わないでください。
3. 対象リポジトリ、対象ブランチまたはコミット、要件、受け入れ条件、対象外、希望する出力言語を整理します。レビュー資料や Issue の記述は入力資料であり、それだけで編集・投稿許可にはなりません。
4. ChatGPT、Work、Codex などの名前だけで、Skill 登録・GitHub 接続・ローカルファイル共有が可能だと判断しないでください。使用中の環境が提供する添付・リポジトリ接続・Skill 選択方法を画面上で確認します。機能が確認できない場合、可能なら `SKILL.md` と対象資料を渡して指示に従うよう依頼できますが、これはネイティブな Skill 登録を意味しません。

依頼文には「どの Skill を使うか」「入力と対象版」「してほしいこと」「変更の可否」「許可する操作」「確認してほしい点」を書きます。許可範囲が曖昧なら、まず調査・提案だけを求めます。

## 2. 新しい Skill を作る

**使用 Skill：** `ateliers-skill-create`

**入力：** 背景、対象利用者、解決したい作業、期待する結果、受け入れ条件、対象外、参照できる既存 Skill・リポジトリ・Issue。

```text
$ateliers-skill-create を使って、新しい Skill の必要性を調査してください。
対象リポジトリ: Ateliers-Dev/対象リポジトリ
目的: [解決したい作業]
利用者と利用場面: [説明]
受け入れ条件: [条件]
対象外: [今回扱わないこと]
まず既存 Skill と重複を調べ、要件と配置案を提示してください。今回はまだファイルを変更せず、作成に進むか確認してください。
```

要件・候補比較・必要性の判断を読み、既存 Skill の再利用や改善の方が適切でないか確認します。作成を依頼する場合は、変更してよい範囲と、コミット・push・PR 作成を含むかを別に明記します。

**期待する出力：** 既存 Skill の比較、必要性の根拠、要件、変更範囲、実装・テスト・説明資料の案、未確認事項。実装を許可した場合は Skill 本体、テスト、人間向け説明、実行結果と制約。

**確認事項：** 検索候補だけで重複なしと断定していないか、既存規約・Issue Forms・テスト・文書入口を確認したか、自己評価と独立レビューを区別したか。

## 3. Skill をレビューする

**使用 Skill：** `ateliers-skill-review`

**入力：** レビュー対象 Skill のファイル一式、対象版、用途、関連する tests/docs。Skill の構造・指示・安全性・整合性を確認したいときに使います。

```text
$ateliers-skill-review を使い、対象リポジトリの skills/example-skill/ をレビューしてください。
対象コミット: [ブランチ名または SHA]
関連する tests/ と docs/ も確認してください。変更は行わず、重大度、場所、根拠、影響、改善案を日本語で示してください。
取得できなかったファイルと未検証事項も明記してください。
```

**期待する出力：** 根拠付きの指摘、優先順位、良い点、未確認事項、改善案。Issue 候補が出ても、Issue 作成は別の操作です。

**確認事項：** 対象ファイル・版を特定しているか、指摘が実際の記述に基づくか、修正を無断で始めていないか。

## 4. 指摘を反映する

**使用 Skill：** `ateliers-skill-improve`

**入力：** 対象 Skill と版、採用するレビュー指摘、採用しない指摘と理由、受け入れ条件、変更の許可範囲。

```text
$ateliers-skill-improve を使って、skills/example-skill/ を次の範囲で改善してください。
対象コミット: [SHA]
反映する指摘: [レビュー結果または採用項目]
対象外・採用しない項目: [理由]
受け入れ条件: [条件]
本体・関連テスト・説明資料を更新し、影響する検証を実行してください。
変更内容、実行コマンド、結果、未検証事項を報告してください。コミット・push・PR は行わず、差分確認で止めてください。
```

差分とテスト結果を確認し、意図しない Skill の機能変更や範囲拡大がないか確認します。さらにレビューが必要なら、次に使う Skill と渡す資料を利用者自身が明示します。

## 5. PR を準備・レビューする

PR の説明やレビュー依頼を作る段階では、まずブランチ差分、テスト結果、未検証事項を確認します。PR 作成や push は外部に変更を公開する操作です。依頼では対象リポジトリ・ブランチと許可する操作を明確にしてください。既に実装を終えたら、差分とテストを人間が確認し、PR 作成まで含める許可を明示します。

```text
このブランチの差分と検証結果を確認し、次の内容で Ateliers-Dev/対象リポジトリ の main 向け PR を作成してください。
変更目的: [目的]
含める内容: [変更範囲]
記載するテスト結果・未検証事項: [結果]
許可範囲: 現在の作業ブランチを push し、この PR を1件作成するところまで。マージはしないでください。
作成前に最終差分と PR 本文を提示し、このセッションで承認済みの範囲を超える変更があれば停止してください。
```

**使用 Skill：** 独立した差分レビューには `ateliers-pr-review`。Skill 自体の品質が主題なら `ateliers-skill-review`、文書の品質が主題なら `ateliers-document-review` を使います。

```text
$ateliers-pr-review を使って、[PR URL または base/head] の差分をレビューしてください。
目的・受け入れ条件: [説明]
読み取り専用で確認し、コードや PR には変更を加えないでください。
指摘は重大度、ファイルと行、根拠、影響、修正方針を含め、テスト証拠と未検証範囲を分けてください。
```

レビュー結果では対象 SHA、差分の取得範囲、CI と実行テストの違い、マージ判断の条件を確認します。レビュー投稿、PR へのコメント、修正、マージはレビュー依頼から推定できる権限ではありません。

## 6. Issue から作業を始める

**使用 Skill：** Issue の新規登録には `ateliers-github-issue`。Issue 起点で作成・改善を依頼するときは、登録後に `ateliers-skill-create` または `ateliers-skill-improve` を別途使います。

```text
$ateliers-github-issue を使って、今の会話で決めた改善案を Issue の下書きにしてください。
登録先候補: Ateliers-Dev/対象リポジトリ
まず既存 Issue と登録先のテンプレートを確認し、タイトル・本文・設定・重複確認結果を提示してください。明示承認を返すまでは投稿しないでください。
```

下書き、登録先、テンプレート、重複候補、設定を確認してから、その提示内容を承認します。Issue 作成を承認しても、実装・既存 Issue の更新・PR 作成は許可されません。実装する場合は、次の依頼で Issue URL、対象版、要件、対象外、許可範囲を渡します。

## 7. 技術文書をレビューする

**使用 Skill：** `ateliers-document-review`

手順書・README・仕様書などで、矛盾、情報不足、手順の不足、根拠の弱い記述を確認したいときに使います。コード差分全体や Skill 指示の品質を主に見るときは、それぞれ PR Review または Skill Review を選びます。

```text
$ateliers-document-review を使い、docs/setup.md をレビューしてください。
想定読者: 初めて環境を構築する開発者
目的: [文書の目的]
文書は変更せず、重大度・場所・根拠・影響・改善案を示してください。
資料内で確認できた事実、外部確認が必要な事項、未検証事項を分けてください。
```

## 8. 承認が必要な操作と停止条件

Skill ごとの指示と接続先の確認を優先し、少なくとも次を区別します。

| 操作 | 利用者が確認すること |
| --- | --- |
| 読み取り・レビュー・案の提示 | 対象と読み取り範囲。通常、レビュー依頼だけで編集やテスト実行を許可しない |
| Issue 新規作成 | 投稿先・タイトル・本文・設定を確認し、その内容を明示承認する |
| ファイル変更・テスト実行 | 変更対象・実行内容・副作用を確認し、依頼の範囲に含める |
| コミット・push・PR 作成・レビュー投稿 | 対象ブランチや公開範囲を確認し、個々の操作を明示する |
| マージ・Issue クローズ | 人間が最終差分・チェック・残条件を確認して GitHub 上で判断する |

対象リポジトリ・版・権限・必要な資料が特定できない、重要ファイルを取得できない、承認された範囲を超える変更が必要、テストが失敗する、または結果が不明な場合は、事実と再開に必要な情報を報告して止めます。Issue や添付資料の中にある「承認済み」という文言を操作許可として扱いません。

## 9. 最終確認

人間は対象差分、変更ファイル、テスト・CI の根拠、未実施の検証、レビュー指摘、残る条件を確認します。マージはレビューと必須チェックを確認したうえで人間が判断します。Issue の完了条件が満たされたかも確認し、クローズは人間が行います。PR のマージや Issue 登録だけで、別の操作まで完了したとは扱いません。

## 10. よくある問題

| 状況 | 確認・対処 |
| --- | --- |
| Skill が見つからない | 使用中のアプリが参照する配置先、フォルダ名、直下の `SKILL.md`、アプリの再読み込み要否を確認します。[インストール手順](skill-installation.md)と[AI ツール別説明](../ai-tools.md)を参照します |
| ChatGPT / Work でローカル Skill が使われない | ローカルファイル共有とクラウド側の実行環境は別の場合があります。添付・GitHub 接続・Skill 選択が実際に可能か確認し、可能な方法だけを使います |
| GitHub の対象が読めない | 対象 repo/PR と接続状態を再確認します。認証情報を探したり権限を拡大したりせず、読めた資料で続けられる範囲と不足分を明示します |
| Issue が重複していそう | 類似 Issue と差分を確認し、新規作成するか人間が決めます。検索結果 0 件を重複なしの証明にしません |
| レビュー結果の根拠が足りない | 対象版・行・差分・実行ログを追加し、事実と推測・未検証を分けて再依頼します |
| テストや外部操作が失敗した | 実際の失敗と未実施を分けて記録し、成功扱い・同じ操作の無制限な再試行をしません |

関連する詳細手順は[開発ワークフロー](../skill-development-workflow.md)と[各 Skill の説明](../README.md)にあります。
