# レビュー知見

作成日：2026-11-06 ／ 更新日：2026-11-06（日本標準時 JST (UTC+09:00)）

レビューで得た事例と、他の変更にも適用できる確認観点を保存します。共通運用ルールの正本は [standards/](../../standards/README.md) です。[共通品質基準](../../standards/quality.md)に従い、日本語と通常の Markdown で、事実・報告・推測・未確認を区別します。

## 事例とパターンの役割

- `cases/`：特定の PR・コミットで、何が問題となり、どう修正・検証されたかを記録します。履歴と証拠を保持します。
- `patterns/`：事例から一般化したレビューの問いを記録します。適用先の仕様・OS・実行環境を確認して使います。すべての変更への必須チェックや、問題の完全検出を保証するものではありません。

`knowledge/` は知見の編集正本の保存先です。`knowledge/` 自体は配布せず、対象パターンを `skills/ateliers-pr-review/references/` へ機械生成して Git 管理・同梱します。Phase 3 PR A は配布・同期基盤までです。Skill 本体の条件付き参照・フォールバック、PR #9 を使う行動評価、Issue #10 の完了判断は PR B に残します。

## 同梱資料の生成と照合

編集するのは `patterns/filesystem-path-safety.md` だけです。対応する `skills/ateliers-pr-review/references/filesystem-path-safety.md` は直接編集しません。リポジトリルートで、正本の変更後に次を実行し、正本と生成物の差分を一緒にコミットします。

```text
npm run knowledge:generate
npm run check
npm test
```

`scripts/sync-review-knowledge.mjs` は引数なし、または `--check` では読み取り専用の照合です。`--write`（上記の生成コマンド）だけが生成物を書き換えます。`npm run check` は欠落、手編集、正本更新後の未同期を失敗として報告し、自動修復しません。新しい配布対象が必要になったら、スクリプト先頭の対応一覧に正本と生成先を追加します。

出力は UTF-8（BOM なし）、LF、末尾改行1個に固定します。正本も BOM・改行を正規化した本文の SHA-256 を計算し、直接編集禁止・正本パスとともにヘッダーへ記載します。日時・作業場所・HEAD は出力に含めません。生成物の LF は `.gitattributes` でも固定します。

通常の単行 `[ラベル](URLまたは相対ファイルパス)` を扱います。相対リンクは存在するリポジトリ内ファイルを確認し、`https://github.com/Ateliers-Dev/ateliers-ai-skills/blob/main/` 以下の絶対 URL に変換します。補足の事例・更新案内は main を参照し、既存の HTTP(S) URL（固定コミットと行アンカーを含む）は保持します。コードスパン・コードフェンス内の例は変換しません。画像、参照形式、HTML、自動リンク、タイトル付き・複雑なリンク、HTTP(S) 以外の方式、認証情報付き URL、リポジトリ外・不存在の参照などはエラーにします。対応外の構文を追加する際は生成器とテストの更新が必要です。

同梱本文には6観点の適用条件・問い・入力例・必要な証拠・限界・出典が残り、レビュー観点を読むためのローカル `knowledge/` やネット接続は不要です。補足リンク先の閲覧にはネット接続が必要です。生成テストは同期・リンク変換・単独配布の内容を確認するもので、AI のレビュー行動や欠陥検出率の評価ではありません。

## 記録項目

事例・パターンの両方に、対象技術、適用条件、根拠、確認状況を見出し等で明記します。複雑なメタデータや専用検索基盤は使いません。

事例には対象 PR、base/head、修正コミット、関連 Issue、問題・原因・影響・修正・回帰テストの対応、検証主体・対象版・方法・結果・未実施項目、出典を記録します。パターンには適用条件、確認する問い、入力例、必要な証拠、限界、出典事例を記録します。相互リンクを付け、入口の一覧も更新します。

## 証拠区分

| 区分 | 記載する内容 | 扱い |
| --- | --- | --- |
| コード・差分の静的確認 | 固定コミット、ファイル、確認した処理 | 実行成功の証拠とはしない |
| 独立した実行確認 | 検証者、対象版、環境、入力、実行範囲、結果 | 部分検証を統合テスト全体の成功へ拡張しない |
| 作者・ユーザーの報告 | 報告者、出典、報告された範囲、ログの有無 | 文書作成者自身の再実行と区別する |
| GitHub 上の事実 | PR 状態、head、マージ SHA、日時 | マージ済みでも、未確認テストや CI の合格を推定しない |
| 推測・一般化・未確認 | リスクの条件、導いた問い、未実施理由 | 再現済みの現象や確定した被害と区別する |

コードの根拠はブランチではなく固定コミットにリンクします。PR 本文・Issue・会話は更新や閲覧制限があり得るため、取得日と必要な要約を残します。会話へのリンクだけで内容を読めるとは限りません。ログが得られなかった場合は、その制約を明記します。

## 更新方法

1. 既存事例・パターンとの重複と適用条件を確認します。既存知見で足りる場合は新設しません。
2. 固定コード・差分と報告を照合し、検証主体・対象版・証拠区分ごとに記録します。
3. 追試や追加報告は、元の時点の未確認事項を消さずに追記します。結果が食い違う場合も両方の条件と根拠を残します。
4. 作成日を保持し、更新日を JST の更新日にします。相対リンク、見出し、日付、出典、変更範囲を確認し、リポジトリのチェックと未実施項目を PR に記録します。
5. 人間のレビュー・承認・手動マージを経て保存します。知見の保存だけで既存 Issue をクローズしたり、Skill の動作を変更したりしません。
