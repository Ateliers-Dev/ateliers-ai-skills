# Skill 作成のテスト

実際の初回作成依頼（PR Review）での工程・判断・検証・公開と Create の評価は [E2E 記録](e2e-pr-review.md) を参照してください。初版試行、入力版 v2 の組み立て確認とは別の実行です。

Node.js 18以上でリポジトリルートから実行します。依存は package-lock.json の yaml 2.9.1 です。未導入時は内容を確認して npm ci を行います。

```text
npm run check
npm test
node --test tests/ateliers-skill-create/create.test.mjs
git diff --check
```

既存チェッカーは構造・リンク・docs 日付・4 Forms、追加テストは実リポジトリの Create 登録と Catalog の CLI/API 連携を確認します。AI の意味的判断・行動は自動採点しません。fixture や生成器の一律導入も要求しません。

## 共通準備と単独実施

1. 対象コミット、未コミット差分、入力ファイルの SHA-256 を固定し、[プロンプト](prompts.md) から一つの ID を選ぶ。初版結果の入力とは区別し、現行を入力版 v2 とする。
2. ケースごとにクリーンな一時作業コピーを用意する。既存 skills・standards・scripts・依存とロックファイル・Forms・構造検証用 tests/docs を同じ対象版から揃える。前ケースの生成 Skill・コミット・操作結果は持ち込まない。コミット試験は一時 Git の作業ブランチで行い、実 remote への書き込みは無効にする。実リポジトリや実サービスを変更しない。
3. 試験対象 AI のコンテキスト・アクセス可能な作業コピーから、この Create 試験の expected.md、validation.md、e2e-pr-review.md、results/、過去回答・作者の採点を除外し、評価者側に保持する。README・prompts.md も丸ごと渡さず、共通の権限境界と選択ケースだけを展開する。構造検証用スクリプト等の他 tests は必要な範囲だけ渡す。
4. AI に Create 本体と、選んだ行の入力全文・実行依頼・許可範囲を渡す。模擬条件は実施者が保持し、該当段階で返す。新しいコンテキストを使い、期待事項・作者回答を先渡ししない。B1 は追加の入力ファイルなし。S1 は本体・指定入力・依頼のみで、共通資産の欠落自体が条件。
5. M1/D2 の未定事項、C1 の未読、S1 の欠落は意図した条件として記録する。それ以外の必要資料・応答が不足したら準備漏れとして区別し、勝手に別ケースから補わない。
6. 回答・作成物・操作履歴を固定してから、評価者が [期待事項](expected.md) を読み採点する。作者が期待を知って試した場合は非盲検自己試行とする。独立行動試験と差分への独立レビューはそれぞれ別に記録する。

## 入力組み立ての例（AI 行動の合格ではない）

### 直接記載：N2

Create 本体と共通の権限境界に、inputs/issue.md の全文と N2 の実行依頼・許可範囲を続ける。模擬応答なし。他ケースの権限・会話・実行結果は参照しない。短い依頼はこのように直接記載すればよい。

### 共有資料・固定会話：P1

inputs/normal.md の全文を共有要件として使う。inputs/approval.md の冒頭から「承認発言（user）」末尾までを会話順に展開し、P1 の実行依頼・許可範囲を付ける。fixture 後半の「模擬ツール応答」は実施者側に保持し、模擬 push 段階でのみ返す。PR 本文全文・登録先・head/base・draft・タイトルと、それを承認する発言が一緒に入っているか照合する。

この提示済み文案は過去会話の条件であり、今回の正解回答ではない。mock の承認は実外部操作の許可にはならない。通常要件・承認・拒否応答を条件ごとに分け、別のケースへ承認や拒否を流用しない。fixture のファイル形式はこの例に限定しない。

### 組み立て後の確認

選択 ID、対象版、資産の版・パス、展開済み入力、実施者側の応答を照合する。「N1 と同じ」等の未展開参照、他ケースの結果、期待事項・作者回答・採点記録の混入がないか確認する。代表ケースだけを選び、別の空の作業場所でも同じ入力を組み立てられるか確認し、入力と資産のハッシュを保存する。この確認では AI の生成・操作は評価できない。

## 記録と入力改訂

回答・ログ・入力展開結果は `results/<実行ID>/` に保存し Git 管理から除外する。追跡対象の [検証記録](validation.md) には実行別の要約と入力の識別子を残す。記録項目の配置・形式は固定しない。

| 項目 | 記録する内容 |
| --- | --- |
| 対象・入力 | ケース ID・目的、対象コミットと差分の識別子、入力版・各ファイルと展開結果のハッシュ、必要資産・前提・意図した欠落 |
| 実行 | 実行 ID・日時（JST）、入力組み立て／構造検証／自己試行／独立行動試験／独立レビュー、方法・コマンド、許可範囲、返した模擬応答 |
| 主体・証拠 | AI 製品・モデル・環境・ツール、実施者・評価者、期待を事前に知っていたか、回答・操作・成果物の保存場所 |
| 結果・限界 | 結果・失敗・スキップ理由・未実施範囲。不明は不明と書く。模擬拒否を実サービス拒否の証拠にしない |

入力を変更したら旧版・旧結果を残し、新しい入力版と実行 ID を作る。旧入力への自己採点を新版の合格として転記しない。再実施したケース・方法と未検証のケース・行動を区別する。独立行動試験や実サービス書き込みは一律必須ではない。未実施なら未検証と記す。
