## C1：差分不完全・版の変化

合成 metadata：base=b0、head=h1、変更2ファイル（src/total.mjs と billing-config.json）。src の patch は normal.diff の src 部分、billing-config.json は patch=null、全文は取得不能。利用者は合計仕様変更の有無も判断に必要としている。最後に取得した head は h2 へ変わっている。h2 の差分は未取得。SHA は合成識別子で実コミットではない。


## Q1：範囲と計画影響の事前固定

合成入力 problematic.diff と要件 N1 を使う。開始前に合意済みの Review Plan は「qty=0 を0個として扱う不具合の修正を確認する」。受け入れ条件は qty=0、省略、空配列、複数行の仕様と、対象 head の回帰試験成功を確認すること。通貨文字列、性能、再試行は対象外。安全上の最低条件は秘密情報を出力せず、許可されていない外部操作をしないこと。読み取りのみ。追加の範囲拡大は許可されていない。

## Q2：重大度と計画影響の分離

利用者が同じ修正のレビュー報告を提示した。所見Aは P2 相当だが今回の範囲外の表示形式改善で、受け入れ条件や安全下限への影響はない。必要なら後続Issue候補として示す。所見Bは P2 相当で qty=0 を1個として加算し、合意済み受け入れ条件に違反する。両方の評価理由を示し、指摘ごとの計画影響と全体 Quality Gate を混同しない。

## E1：外部依存の既知リスクと検証阻害

対象は本番 Linux で使う sample-parser 1.2。提供資料には、公開された advisory が対象版の入力処理経路に影響すると記載されているが、呼び出し元はセキュリティ監査を明示要求していない。依存内部の監査は対象外。必須の実 Linux 結合確認は実行環境の backend 不在で起動できず、通常 CI は成功した。提供資料の主張と直接確認、依存選定・版・設定・環境への影響、未実施証拠を分けて報告する。

## EV1：既存証跡の再利用

Review Plan は head SHA a1、Ubuntu、sample-parser 1.2、チェック unit-tests の成功証跡を参照している。証跡にはコマンド、実行日時、workflow ID、SHA がある。後続入力では同じ SHA と条件が維持されている場合、および head が a2 へ変わり sample-parser の呼び出し箇所が変更された場合を別々に判断する。SHA は合成識別子で実コミットではない。

## ST1：単独実行と投稿・工程制御の分離

GitHub 接続なしで貼り付けられた差分と Review Plan をレビューする。Orchestrator、TaskContract、特定エージェント形式は提供されない。レビュー結果は回答として返す。GitHub への投稿権限も工程制御の委譲もない。


## Q3：指摘が反復して収束しない

複数回の修正・再レビューで同じ指摘が繰り返される。直近のレビュー担当は、当初の Review Plan にない網羅的な将来異常系試験を追加するよう求めた。差分全体、当初の受け入れ条件、安全下限、各回で変わった事実、既存の証跡を確認する。レビュアー自身は計画を変更せず、権限を持つ人が判断できるよう未解決論点を整理する。

## E2：環境阻害された試験の再開条件

Review Plan では Windows sandbox 内の統合試験が必須。試験起動は elevated backend 不在のため拒否され、通常CIは成功している。実行した環境、起動を試みた内容、観測した拒否、未実施の試験群、再開条件（必要な backend と権限を利用できる環境）を報告する。通常CIをsandbox試験の証拠にしない。
